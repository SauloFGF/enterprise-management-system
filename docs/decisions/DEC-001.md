# DEC-001 — API error contract

**Status:** APPROVED  
**Date:** 24/09/2026  
**Owner:** Tech Lead

## Decision

Use RFC 7807 `application/problem+json` for API errors. Responses contain `type`, `title`, `status`, `detail`, `instance`, `correlationId` and, for validation errors, an `errors` collection keyed by field.

Use `400` for malformed/invalid input, `401` for missing or invalid authentication, `403` for insufficient role, `404` for a resource not found, `409` for duplicate or invalid state conflicts, `429` for rate limiting and `500` for an unexpected server error. Do not return stack traces in production.

## Rationale

ProblemDetails is standard, interoperable and avoids a custom error format. The status mapping gives the frontend and E2E tests stable behavior.

## Impact

Applies to TASK-004, all endpoint tasks and frontend error handling (TASK-013).

## Evidence

Specification requires documented APIs, validation and security; this record supplies the missing contract without changing product behavior.
